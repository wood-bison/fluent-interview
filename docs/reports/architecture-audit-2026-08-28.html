01Область работы и допущения

Аудит без правок кода: ни одна строка исходников в пяти дочерних репозиториях не изменена. Цифры ниже привязаны к коммиту umbrella 76419a5 и артефактам W07/W22; команды воспроизведения — в разделе 19. Одна честная оговорка: ранее запущенные гейты workspace перезаписали поля generatedAt в собственных файлах-доказательствах — это побочный эффект проверки, а не изменение продукта.

Явные допущения

  • CRUD-Only. Рассматривается только существующая CRUD/чтение-поверхность. Новая продуктовая функциональность в план не входит — это ваше ограничение: «пока это всё только CRUD-Only».
  • Vue → Next.js — исторически записанное решение владельца, но не вывод аудита. Текущий learner UI, пакет контрактов, Playwright-матрица и действующие инструкции репозитория являются Vue-native. До повторного явного подтверждения этот пункт считается стратегическим decision gate, а не разрешением удалить Vue.
  • Монорепо — второй decision gate. AGENTS.md прямо говорит: «This directory is a workspace umbrella for five independent repositories. It is not a source monorepo». Поэтому безопасный план сначала исправляет внутреннюю связанность и кросс-репозиторные контракты, а физическое слияние remote-историй выполняется только после отдельного подтверждения владельца.
  • Оценки трудозатрат — порядок величины для одного разработчика, не коммитмент.

Сегодня фраза из AGENTS.md «Do not share PostgreSQL tables, ORM entities, local catalogues, or fallback data between repositories» защищена физически: чтобы нарушить её, нужно опубликовать пакет. Хорошая новость: правила уже написаны и работают в Lab. Задача — не изобрести их, а распространить: раздать теги всем новым проектам, добавить depConstraints для domain:* и integration:*, и сделать nx affected -t lint обязательной проверкой PR.

08TypeScript 7: что проверено эмпирически

Это единственный раздел, где я не рассуждаю, а показываю результаты запусков. Главный риск перехода на TS 7 для Nest — не типы, а эмиссия метаданных декораторов: без design:paramtypes DI молча получает undefined, и это не ловится компилятором.

Что такое TypeScript 7

Нативный компилятор: пакет typescript@7.0.2 весит 3,5 МБ и состоит из загрузчика плюс 21 платформенный бинарник (@typescript/typescript-darwin-arm64 и т. д.). Программный API переехал в typescript/unstable/* — это и есть источник всех рисков совместимости с инструментами, а не сам язык.

Что монорепо реально даёт (и чего не даёт)

Даёт

  • Один git clone — прямо то, что вы просили.
  • Кросс-сервисный CI, которого сегодня нет ни в одном из шести workflow. Контрактные гейты verify:schema, validation:matrix, release:verify начинают исполняться в каждом PR, а не вручную.
  • Атомарный коммит на изменение контракта: сегодня правка HTTP-контракта Brain ↔ Lab — это два PR в двух репозиториях без общего гейта.
  • Конец рассинхрону версий из находки №10: одна версия @types/node, TypeScript, Playwright на всю платформу — структурно, а не по договорённости.
  • nx affected вместо «прогнать всё во всех репозиториях».

Не даёт (и это надо компенсировать)

  • Физическую невозможность нарушить границу. Единственная замена — теги + линтер в CI. Это ядро сделки.
  • Независимую релизную политику «из коробки»: сейчас у каждого репозитория своя. Понадобятся release-теги вида question-brain@x.y.z и правила, что именно собирается на каждый тег.
  • Экономию на CI-времени по умолчанию: без корректных inputs/outputs в целях Nx кэш будет промахиваться, и один большой workflow станет медленнее шести маленьких.

  • Ф5 (декомпозиция) до Ф6 (слияние). Резать монолит внутри одного знакомого репозитория проще, чем сразу после переезда: если что-то пойдёт не так, откат тривиален.

Целевая модель: не один validator, а AssessmentPolicy

Главный вывод из Solvit и собственного кода: разные активности отвечают на разные вопросы. Универсальный boolean passed неизбежно смешивает уверенность, факт запуска, качество объяснения и удержание знания. После рефакторинга каждая Activity должна явно объявлять policy:

AssessmentPolicy {
  mode: selfConfidence | deterministicRun | deterministicRubric | humanReview | portfolioEvidence
  authority: learner | lab | taskRuntime | reviewer
  requiredEvidence: [...]
  mayUnlock: boolean
  retentionPolicy: none | spacedRecall | coldRepeat
  rubricVersion?: string
  evaluatorVersion?: string
}
  • Самооценку сохранить, но переименовать. solid/partial/missed влияет на SRS, не на mastery. В аналитике показывать confidence рядом с independently verified evidence, а не складывать их в один процент.
  • Run и Submit разделить контрактно. Run — быстрый feedback, не закрывает capability. Submit — immutable attempt against pinned TaskRevision и server-owned verdict.
  • Метрики определить до вывода в UI. У Solvit SQL-пример: 17 solved / 43 tried ≈ 39,5 %, но acceptance_rate=11; code-пример: 3998 / 4189 ≈ 95,4 %, но rate 63. Следовательно, rate нельзя вычислять как solved/tried без документации; вероятно, он submission-based или использует другую выборку.
  • Typed content blocks и schema preview. Перенять представление таблиц/relationships как данные. Это полезно независимо от внутреннего validator.
  • Company taxonomy, next/prev, my solutions. Это read-модели поверх уже существующих данных, но каждое поле должно иметь owner, provenance и release version.
  • Граф не считать отсутствующим у конкурента. Публичная learner-поверхность не показывает semantic graph; внутреннее наличие неизвестно. У нас факт другой: W07 release чистый, но пустой; 2 001 related-proposal ждёт editorial review.

Разрезать монолит на доменные библиотеки недостаточно — внутри каждой нужна одна и та же форма, иначе через полгода получится шесть маленьких монолитов. Форма уже частично применяется (app/kernel/lab-port.decorator.ts, port-conformance.ts) — её надо сделать обязательной:

libs/domain/<name>/src/
  model/        # чистые типы и правила. Тег boundary:pure → внешних импортов НОЛЬ.
  ports/        # интерфейсы того, что домену нужно снаружи (репозиторий, клиент, часы)
  use-cases/    # по одному файлу на сценарий; зависят только от model + ports
  adapters/     # реализация портов: postgres, http-клиент, in-memory для тестов
  <name>.module.ts   # единственная точка сборки для Nest: провайдеры и экспорт
  • Что это даёт немедленно. Сегодня в app/persistence/ лежит 26 пар «in-memory + postgres» репозиториев (in-memory-attempt ↔ postgres-attempt, in-memory-recall ↔ postgres-recall и так далее) в одном каталоге вместе с моделями и токенами. В форме выше это один интерфейс в ports/ и два адаптера, выбор — DI-токеном. Каталог перестаёт расти линейно от числа сущностей.
  • Тег boundary:pure уже существует в конфиге ESLint и запрещает внешние импорты. Сейчас его почти никто не носит. На model/ он обязателен — это и есть механическая защита от протечки инфраструктуры в домен.
  • port-conformance.ts (330 строк) уже проверяет соответствие портам — то есть идея в проекте есть, ей просто не дали структуры.

CQRS-lite: разделить 81 GET и 20 POST

Профиль API — read-dominated: 81 чтение против 20 команд, мутирующих ресурсных методов нет вообще. Это ровно тот случай, когда разделение читающей и пишущей моделей стоит дешево и даёт много:

  • Команды (20 POST) — попытка, сабмит, коммит — идут через use-case, пишут события и не занимаются формой ответа. Уже почти так и есть: attempt.coordinator.ts (902 строки) — по сути шина команд, которую стоит нарезать по домену.
  • Чтения (81 GET) — становятся проекциями (read-model) вместо композиции на лету. Сейчас композиция на лету — это learner-route-context.service.ts (1 088 строк), question-brain.library.ts (853), next-action.service.ts (651): три самых больших файла приложения — все три собирают ответ из нескольких источников в момент запроса.
  • Побочный выигрыш — кэшируемость. Проекция имеет версию, а значит у неё появляется ETag и понятная инвалидация (см. раздел 18). Композиция на лету не кэшируется в принципе.

Часть A. Как фронтенд узнаёт, что контент изменился

Предлагаемая схема — четыре слоя, каждый работает сам по себе

№СлойЧто делаетЦена и что даёт
1 ETag на проекциях Каждый GET, отдающий релизную проекцию, возвращает ETag = хэш содержимого. Браузер присылает If-None-Match, сервер отвечает 304. Самое дешёвое и первое. Не нужен ни новый процесс, ни новый порт. У нас уже есть content_hash в question_revision — материал для ETag готов. Работает даже без всего остального.
2 Указатель релиза Один эндпоинт GET /api/release → { releaseId, contentHash, publishedAt }. Фронт держит releaseId в состоянии. Ключевой трюк: releaseId входит в ключ кэша — queryKey: ['question', id, releaseId]. Тогда смена релиза автоматически делает все ключи новыми, и инвалидация не нужна вовсе. Старые данные остаются валидными для истории и evidence.
3 SSE-канал GET /api/events — проекция outbox наружу: content.released, graph.released, attempt.recorded, mastery.changed. Переподключение по Last-Event-ID. Паттерн EventSource в api-client уже реализован — берём его. В браузер уходит только факт «что-то в области X изменилось», без полезной нагрузки: клиент сам решает, что перезапросить.
4 Проекции с версией Read-модели из раздела 17 получают версию, а не собираются на лету. Замыкает круг: без версионированной проекции ETag из слоя 1 нечем считать, а композиция на лету не кэшируется в принципе.

Почему SSE, а не WebSocket

  • Профиль трафика односторонний: 81 GET против 20 POST, коллаборативного редактирования в learner-поверхности нет. Полнодуплексный канал нечем занять.
  • SSE — обычный HTTP: проходит через тот же прокси /api, переживает разрыв через Last-Event-ID, не требует отдельного порта в workspace.yaml.
  • Kafka в браузер не идёт. Kafka (порт 49312) остаётся транспортом между сервисами; наружу выходит только SSE-проекция. Иначе домен утекает в клиент.
  • Порядок внедрения: слой 1 → слой 2 → слой 3. Первые два не создают новых процессов и уже дают корректность; SSE добавляет только «мгновенность».

Три варианта, с рекомендацией

Вар.ПодходКак работаетОценка
A OpenAPI из кода Добавить @nestjs/swagger, декорировать существующие 8 DTO → получить openapi.json → сгенерировать клиент (openapi-typescript / orval) и Go-структуры. B Zod-first рекомендую Единая библиотека libs/contracts на zod — единственный источник. Из неё: TS-типы через z.infer (бесплатно, без кодогенерации), JSON Schema через z.toJSONSchema → Go-структуры и кросс-репозиторный гейт. На Nest — ZodValidationPipe вместо class-validator. Цена: переписать 862 строки DTO с class-validator и постепенно втянуть 84 722 строки lab-contracts.
C Schema-first JSON Schema (или protobuf) — первичный артефакт, из него генерируется во все три языка. Максимальная строгость и языковая нейтральность. Оправдано, если появится четвёртый язык-потребитель. Сейчас — самая высокая цена при том же результате, что даёт B.

Почему B, а не A

  • Направление важнее инструмента. В варианте A правда живёт в декораторах Nest, и Go с браузером получают её из вывода. В B правда живёт в отдельной чистой библиотеке, а Nest — такой же потребитель, как и все. Второе выживает при смене фреймворка; первое — нет. А фреймворк мы как раз меняем (Vue → Next), поэтому цена ошибки здесь реальная.
  • JSON Schema как промежуточный формат в проекте уже принята — docs/contracts/question-capability-task.v1.schema.json написана на draft 2020-12 с $defs и паттернами ключей. То есть B не вводит новый формат, а достраивает существующий путь.
  • Гейт уже существует. pnpm verify:schema проверяет совместимость схем. Расширить его двумя правилами: (1) контракт не собран из zod → CI красный; (2) сгенерированные файлы коммитятся, и после генерации git diff --exit-code должен быть пустым — иначе кто-то правил вывод руками.
  • Где живёт: libs/contracts/* с тегом boundary:pure — внешних импортов ноль, кроме самого zod. Тогда контракт не может утащить за собой рантайм-зависимость, а это ровно тот класс ошибок, от которого правило и придумано.
  • Порядок: начать с одного домена — не с самого большого. Хороший кандидат — контракт Task Runtime: он уже описан в трёх местах (lab-contracts/task-runtime.ts 911 строк, Go-структуры, zod на фронте) и имеет узкую границу. Один домен целиком покажет реальную цену до того, как трогать остальные.

Обе части — после Ф5 (декомпозиция) и до Ф7 (Next). Причина одна: генерировать DTO из плоской кучи на 84 722 строки бессмысленно, а переписывать фронтенд на Next, не имея сгенерированного клиента, — значит добавить ещё одну рукописную копию контрактов.
