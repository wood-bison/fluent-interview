От вопроса к доказуемому навыку

Это не ещё один список карточек. Целевой production-сценарий — взять одну QuestionCard, понять теорию и system design, открыть связанный TaskBrief, выбрать язык, выполнить неизменяемую ревизию и получить проверяемое Evidence. Ни один слой не подменяет другой.

Вердикт в одной фразе

Архитектура правильная, если Question Brain публикует смысл, Task Runtime исполняет код, а Fluent Lab только строит путь и показывает доказательства. Сейчас нужно закрыть связи, проекции и release-gates, а не добавлять ещё один каталог.

Не складывать в одну сумму

  1. 1Card — что нужно уметь объяснить.
  2. 2Capability — какой навык проверяет карта.
  3. 3Route step — станция, в которой Lab её показывает.
  4. 4Task — практический brief с одной или несколькими ревизиями.
  5. 5Run / Evidence — конкретная попытка и её доказательство.

Как читать числа в интерфейсе

Programнабор треков и доменов, а не карточки. В production лучше переименовать в Tracks.
Knowledge Mapвизуальная карта capability и связей. Счётчик показывает projection nodes, рядом нужен вопросный coverage.
Questionsинвентарь карточек из Question Brain. Одна карта может быть в нескольких темах и путях.
Openразрешение открыть станцию/карточку в выбранном режиме, а не признак существования контента.
02 · domain model

Одна цепочка, пять сущностей

QuestionCard и задача связаны, но не являются одним объектом. Это позволяет объяснить идею устно, затем проверить её кодом, SQL или system-design сценарием.

01 / SEMANTIC

QuestionCard

Короткий ответ, теория, traps, follow-ups, локали и provenance.

Question Brain
02 / PRACTICE

TaskBrief

Контракт задачи: цель, вход, ограничения, rubric и capability, которую проверяем.

Question Brain
03 / EXECUTABLE

TaskRevision

Языковой вариант brief: starter, tests, toolchain, limits, revision id.

Task Runtime
04 / OBSERVED

Run

Одна попытка в sandbox с профилем, commit-like input и статусом.

Task Runtime
05 / PROOF

Evidence

Trace, score, tests, explanation и связь с прогрессом learner.

Lab + Runtime
Ключевой контракт: Question Brain публикует смысл и ссылку на TaskBrief; Runtime никогда не переписывает ответ на вопрос; Lab не копирует карточки и не решает, что «правильно». Lab показывает release-scoped projection и сохраняет learner progress.

QuestionCard · «Спроектируй rate limiter» canonical key: question.q315 · release 15e032d7b732f8c1
карточка опубликована

Как ограничить поток запросов и не разрушить сервис?

Устно объяснить алгоритм, выбрать границы состояния и показать, как решение ведёт себя при burst, retry и распределённом размещении.

Теория и короткий ответ

Token bucket ограничивает среднюю скорость, допускает контролируемый burst и требует явных правил clock, reset и bounded state.

System-design разбор

Сначала single-node invariant, затем shared state, consistency, hot keys, retry policy и наблюдаемость.

TaskBrief · «Реализовать token bucket»

TB-RL-001 · planned
  • Вход: clientId, timestamp и последовательность запросов.
  • Цель: не больше 5 запросов за 10 секунд на клиента, burst — по спецификации.
  • Rubric: correctness · boundary · bounded memory · explanation.
  • Один brief допускает несколько валидных языковых ревизий, но не общий исходник.

04 · boundaries

Три владельца — один контракт

Никаких общих таблиц, локальных каталогов и скрытых fallback. Сервисы обмениваются versioned HTTP/event contracts и immutable release ids.

Question Brain

Редакторская и семантическая истина.

  • QuestionCard, ответы, локали, provenance.
  • Topics, capabilities, typed edges.
  • TaskBrief и связь capability ↔ brief.
  • Release, search и embeddings.

Task Runtime

Единственный исполнитель пользовательского кода.

  • TaskRevision и language manifest.
  • Starter, public/hidden tests, limits.
  • Sandbox, Run trace, score и diagnostics.
  • Профили Node, Go, Java, .NET, Postgres.

Fluent Lab

Продуктовый путь и learner state.

  • Projection выбранного Question release.
  • Tracks, modes, route и unlock rules.
  • Progress, recall, journal и evidence view.
  • Только кэш, который можно пересобрать.
Событие Пишет Читает Гарантия
question-release.published Question Brain Lab, indexer release immutable; locale coverage проверена
task-release.published Task Runtime Lab revision с profile, tests, resource limits
run.completed Task Runtime Lab, observability run id immutable; raw secrets и hidden tests не покидают runtime
evidence.attached Lab learner, recall ссылка на question release + task revision + run

Решение: оставляем три репозитория. Если появится общий contracts repository, в нём будут только схемы и сгенерированные клиенты — не Question Cards и не task code.

05 · route semantics

Путь — это фильтр, не замок

Трек задаёт контекст (например, Backend · Node.js), capability — цель станции, а карточки и задачи являются доказательствами. Любой released вопрос должен находиться через поиск и Explorer, даже если он ещё не входит в Recommended.

01 · TRACK

Backend · Node.js

Основной стек и язык. Это не ограничение содержимого Question Brain.

02 · DOMAIN

Runtime / HTTP / Postgres

Крупные области, которые дают понятную карту, а не 1 392 пункта меню.

03 · CAPABILITY

Rate limiting

Проверяемый навык с prerequisites, related cards и TaskBrief.

04 · EVIDENCE

Explain → Run → Repeat

Теория, практика, холодный повтор и trace определяют прогресс.

RecommendedСледующий capability рассчитан по prerequisite и evidence. Это совет, не блокировка.
ExplorerОткрытая карта: можно перейти к любой released capability и увидеть, чего не хватает.
FreelyПрямой поиск по Question Brain; карточка доступна даже без route binding.

Для UI нужно переименовать счётчики: Tracks вместо неоднозначного Program, Capabilities рядом с map count и отдельный Question coverage. Тогда «15», «79» и «1 392» перестанут выглядеть взаимоисключающими.

07 · acceptance

Как поймём, что это готово

Проверяем не только красивый экран. Production-готовность — это воспроизводимая связь контента, графа, runtime и evidence после перезапуска.

Сценарий Проверка Ожидаемый результат Gate
Найти новый вопрос Поиск по RU/EN, topic, capability и похожему смыслу. Карточка находится в Freely даже без Recommended binding. G1/G2/G5
Открыть rate limiter Deep link из map и из search. Теория, design, TaskBrief и статусы ревизий видны без «закрытого тупика». G2/G6
Выбрать Go Запустить released revision в sandbox. Правильная questionKey, deterministic tests, run id и trace. G3/G4
Перезапустить стек Compose down/up без удаления durable volumes. Release ids и evidence сохраняются; projection rebuild повторяем. G1/G7/G8
Разобрать неделю ошибок Jaeger/metrics: search zero-result, map gap, run failure, latency, memory. Можно назвать capability и шаг, где learner застрял, без raw secrets. G7

Оптимальный сценарий реализации

  1. Сначала выпустить truth ledger и relation validator, не меняя визуальную семантику вслепую.
  2. Пересобрать projection из Question Brain release и показать coverage отдельно от количества узлов.
  3. Починить один capability end-to-end на rate limiter: карточка, brief, Go/Java, затем Node/SQL.
  4. После доказанного vertical slice массово обогащать банк и добавлять языковые ревизии.
  5. Включить modes и unlock rules, затем удалить stale/legacy paths и оставить только release-driven данные.
  6. Закрыть observability, performance, recovery и только после этого назвать сборку production.

Release checklist

Нет локального Question catalog и fallback в steady state.
Каждый displayed count имеет тип, release и timestamp.
Нет orphan question, TaskBrief или TaskRevision.
RU/EN, deep links, keyboard и dark/light не ломают layout.
Run trace и Evidence связаны, но hidden tests остаются приватными.
Rollback/reindex проверены на чистом Compose stack.

Что этот документ утверждает

Финальная проверка против упрощений и противоречий: live, plan и stale явно разделены.

live Подтверждено

  • Question Brain quality: 1 392 published, graph accepted, en/ru coverage и embedding checks без warnings.
  • Lab questions endpoint читает source question-brain с тем же release id.
  • Task Runtime отвечает: 18 tasks, пять runtime profiles, четыре rate-limiter revisions.

plan Нужно сделать

  • Добавлять языковые revisions по мере покрытия capability, не копируя исходники.
  • Снять недельный observability baseline, уменьшить bundle-budget warnings и подписать production release G8.

stale / contradiction Не принимать за truth

  • «Program 15» и «Knowledge Map 79» без типа projection и release.
  • PDF-утверждение про 172 learner-visible и вторую копию Lab — это старый baseline; live API сейчас сообщает source question-brain/1 392.

definition of done Высший вариант

  • Пользователь видит всю released базу через Search/Explorer и понятный рекомендованный путь.
  • Для каждой capability видно: cards, theory, TaskBrief, доступные языки и evidence.
  • Система сама ловит неверные ссылки, дубликаты, missing locale и orphan bindings до release.
  • Любой экран восстанавливается из release + learner events без второго владельца данных.
