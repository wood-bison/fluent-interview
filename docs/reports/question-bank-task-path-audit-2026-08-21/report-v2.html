Как правильно связать вопросы, задачи и пути

Оптимальная модель для нас — не «вопрос превращается в задачу» и не одна огромная база. Это единый граф компетенций, поверх которого живут три независимых слоя: editorial content, executable runtime и learner projection.

Оставить 3 репозитория. Добавить типизированный pipeline.

Question Brain отвечает за смысл и связи. Task Runtime отвечает за безопасное исполнение. Fluent Lab отвечает за маршрут, прогресс и доказательства.

Лучший сценарийНе публиковать контент, пока для него не существует явной связи, рубрики и проверяемого состояния release.

Кто чем владеет

Граница нужна не ради микросервисов. Она защищает смысл от запуска и запуска — от UX.

Почему не сделать одну сущность «QuestionWithCode»

Один и тот же вопрос может иметь несколько способов доказательства. Rate limiter можно реализовать на Node.js и Go; объяснение остаётся тем же, а компилятор, тесты и лимиты — разными.

Важная поправка к HANDOFF.

В QBrain допустим видимый TaskBrief и ссылка runtime_task_ref. Reference solution, hidden tests и execution limits должны оставаться в Task Runtime.

Пример: rate limiter без копирования карточки

Смысл один, а executable revision выбирается по языку. Переключите вариант — увидите, что меняется только runtime-слой.

03 · CONCRETE EXAMPLE
Q-0421 · «Как ограничить частоту запросов?»QuestionCard → TaskBrief
// видимое условие остаётся тем же
capability: rate-limiting
goal: «не больше 5 запросов за 10 секунд»
input: request { clientId, timestamp }
rubric: correctness · boundary · explanation

// runtime: Node.js 24
runtime_task_ref: task.rate-limiter.node.v1

Что проверяем в Node.js

Версию toolchain, таймеры, конкурентный доступ к bucket, reset и bounded memory.

  • public tests: базовый лимит
  • hidden tests: burst и граница окна
  • evidence: trace + score + объяснение

SQL здесь — отдельная вариация задачи (например, rate limiting на PostgreSQL), а не попытка запускать один и тот же исходник в трёх языках. Это и есть смысл `TaskBrief`: связать одну capability с несколькими валидными доказательствами.

Куда попадают задачи из «Банка вопросов»

Папка — это staging-источник. В production не должны попадать ни случайные дубли, ни задачи без лицензии, ни карточки без понятного владельца.

Классифицируем до импорта.

Каждый материал получает один или несколько типов: oral/theory, code, SQL, debugging, system design, behavioral. Только `code` и `SQL` требуют runtime revision. System design и behavioral могут иметь полноценный TaskBrief и rubric без sandbox.

Пути — это views над одним графом

Не строим 15 независимых программ и не делаем 1 368 станций. Строим capability graph, а поверх него — ясные именованные маршруты.

Лучший сценарий: как сделать правильно с нуля

Это не «быстрее дописать карточки». Сначала фиксируем контракты и release gates, затем наращиваем контент и языки.

06 · RECOMMENDED EXECUTION

Сначала качество связи, потом объём

Каждая следующая итерация должна делать путь более честным: пользователь понимает, что изучает, зачем запускает задачу и какое доказательство получил.

  • Один capability имеет много карточек и много форм практики.
  • Одна карточка может ссылаться на несколько runtime revisions.
  • Draft, proposed и released — разные состояния, а не разные таблицы.
  • LLM может предложить enrichment, но не публикует граф и не оценивает deterministic run.

Чего не делать

  • Не хранить hidden tests в Question Brain.
  • Не импортировать 1 805 файлов напрямую в production.
  • Не открывать всё через fallback, если нет binding.
  • Не превращать каждую тему в отдельную программу.
G0

Контракт сущностей

QuestionCard, TaskBrief, TaskRevision, Run, Evidence; ownership и version rules.

Done when: нет дублирования hidden tests/reference solution между репозиториями.
G1

Graph projection

Добавить capability/stage/route keys, типизированные edges и release binding.

Done when: quality API объясняет каждую unbound-карточку, а learner graph показывает реальную coverage.
G2

Bank intake

Разобрать staging, provenance, дубли, локали, тип материала и приоритеты импорта.

Done when: каждый импортированный источник имеет владельца, статус review и trace происхождения.
G3

Task authoring

Сначала закрыть Node.js, SQL, Go и Java; затем добавлять профили только с тестами и limits.

Done when: каждая runnable capability имеет хотя бы одну released revision и smoke-test.
G4

Route views

Recommended, Explorer, Freely; роли и специализации поверх одного графа.

Done when: любой released вопрос можно найти, открыть и объяснить, почему он в этом route.
G5

Search & observability

Hybrid FTS + embeddings, indexer/outbox, traces для поиска, импорта и run.

Done when: через неделю видно, где пользователь застревает и какой контент требует улучшения.
G6

Production release

Release manifests, rollback, migrations, resource budgets, security review.

Done when: чистый запуск Compose/Nx, health/readiness и повторяемый release без fallback.

Мы не копируем формат. Берём проверенные принципы: syllabus отдельно от упражнений, reusable content, canonical tests и hybrid search.

Собираем эти идеи в три независимых репозитория и один root workspace. Контракты — HTTP/release manifests, а не shared ORM или скрытая общая БД.

Итог в одном предложении

Question Brain должен стать редактором и графом смысла, Task Runtime — доказательным execution engine, а Fluent Lab — красивой оболочкой маршрута и памяти.

08 · FINAL VERDICT
Если начать сегодня.

Сначала закрываем G0 и G1: типизируем связи и публикуем projection. Затем импортируем банк волнами, создаём TaskBrief и только после авторской проверки выпускаем языковые revisions. Когда это станет истинным, экран «всё закрыто» исчезнет не за счёт обхода, а потому что система действительно знает, что можно проходить и какое доказательство нужно получить.
