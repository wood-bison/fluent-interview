Что упущено или ошибочно — находки

F1 · «Brain capabilities = 19» — фактическая ошибка ❌ CRITICAL для glossary

План смешал два разных числа. Реестр Brain содержит 16 активных canonical capabilities (+11 deprecated) — и в живой БД (content.taxonomy_capability), и в манифесте capability-registry-2026-08-25.json. Число 19 — это curriculum_capabilities из /v1/quality, которое код считает как число карточек с binding (postgres.go:1790–1806), и оно же равно числу строк в question_capability (G7-report: bindings=19).

Почему важно: план требует в M0 «один глоссарий», но сам открывает его с перепутанным термином. Правильно: «Brain capabilities: 16 active canonical; bindings: 19 карточек».

F2 · Противоречие числовых артефактов одной даты 🟡 WARNING

План: 15 families / 20 revisions / 19 runnable. Коммитнутая G12-верификация Lab от того же дня (G12-TASK-COVERAGE-2026-08-25.md): releasedTaskFamilies: 14, runnableRevisionCount: 24. Оба источника «официальные». План честно разрешает M0 записать «новые фактические значения», но конфликт двух коммитнутых матрицы/манифеста надо разрешить явно — иначе M1 построит contract tests поверх неверного ожидания.

F3 · «12 обязательных областей» не существует как структуры 🟡 WARNING

Ни в одном репозитории нет списка из 12 областей — это конструкция самого плана (M8). В Lab живут три другие таксономии: 24 модуля TIER1-CURRICULUM-SCOPE.md, 15 доменов/81 станция learner-проекции, 9 путей. Космос Plan 2026 упоминает лишь подмножество тем (vision.md:27–28). Если в M8 появится четвёртый список без явного mapping «12 областей ↔ 24 модуля ↔ 15 доменов» — workspace получит очередную раскоординированную таксономию, с которой план борется.

F4 · Дыра поглощения: ASPIRE-JAEGER-DOCKER план ❌ COVERAGE GAP

M10 нового плана покрывает «один shared Jaeger + failure matrix + Docker lifecycle», но из ASPIRE-JAEGER-DOCKER-PRODUCTION-PLAN-2026-08-25.md (1279 строк, G0–G13) выпала вся операционная консолидация: TypeScript Aspire AppHost вместо launcher-скриптов, центральный OTel Collector, decommission Tempo и двух repo-local Jaeger'ов с trace-parity evidence, Jaeger SPM/дашборды, политика persistent storage (Badger/OpenSearch retention), выделенный BuildKit builder. Grep по новому плану: aspire=0, tempo=0, collector=0, prometheus=0, loki=0, grafana=0.

Рекомендация: это либо осознанное упрощение scope — тогда записать rejected-with-cause в M10, либо принять operational sub-gates из Aspire-плана (AppHost, Collector, trace parity, retention и cleanup). Молчать нельзя: сейчас это выглядит как закрытый вопрос, которым не является.

F5 · Живой Runtime stale относительно main + мусорный контейнер 🟡 WARNING для M0

Запущенный runtime-контейнер собран в 13:51 CEST — до коммитов a82a078…9300e2f, и ведёт себя не как текущий main (в catalogue.go:196–215 противоречивая комбинация released/unreleased теперь невозможна — она fail-closed при загрузке). Плюс висит остаточный smoke-контейнер fluent-runtime-task-node-cpu-bound-002-g15-timeout-valid-* (Up 11 часов) — живое доказательство проблемы cleanup, которую план закрывает только в M7/M10.

Рекомендация: добавить в M0 явные шаги: rebuild/recreate образов перед crawl-baseline и kill зависших smoke-контейнеров с фиксацией в baseline.json.

F6 · Workspace.yaml: shared Trace Explorer назван как Runtime UI 🔵 MINOR

services.task-runtime.ui и ports.questionBrain.jaegerUi указывают на один порт 56686. Это не обязательно конфликт: Runtime отправляет traces в общий Jaeger Brain. Проблема — misleading ownership/name после align shared Jaeger; в M0 нужно заменить поле на neutral observability.traceExplorerUrl и не поднимать второй UI.

F7 · Curl-команды M0 работают только в packaged-режиме 🔵 MINOR

Команды M0 бьют в 49301 (packageApi). При pnpm dev Learning API живёт на 47000, web на 47300. План не уточняет режим стека — агент-исполнитель может решить, что система сломана.

F8 · Review Workbench выпал при поглощении 🟡 WARNING для M6

G9 плана QUESTION-CAPABILITY-TASK (выделенный Review Workbench для bindings) свёрнут в M6 без инструмента. M6 требует классифицировать 1 591 карточку с правилом «embeddings предлагают — человек принимает». Без batch-review UI это крупнейший human bottleneck всего плана: тысячи ручных решений по одной карточке за раз.

Что подтвердилось и сделано хорошо

P1 · Честностная механика плана — главная ценность ✅

Три state machine вместо слова «готово», 21 пункт запрещённых shortcuts, авто-veto MasteryClaim (§9), WAITING_HUMAN вместо перемотки времени, запрет E2E-evidence в human profile. Это редкий уровень anti-self-deception инженерии — большинство «mastery»-платформ ломаются именно здесь.

P2 · Sandbox Runtime уже близок к OWASP best practice ✅

docker_executor.go:220: --network none, --cap-drop ALL, no-new-privileges, read-only rootfs, --pids-limit 256, CPU/RAM/wall-clock лимиты, solution и hidden tests смонтированы :ro, --log-driver none, --pull never, cleanup даже при timeout. Это ровно чеклист OWASP Docker Security Cheat Sheet. Остаётся один gap — образы запинены тегами, не digest (см. R6).

P3 · Дизайн learner loop научно корректен ✅

PredictionEvidence до Run — это pretesting/prequestioning effect (Pan & Sana 2021: преимущество до d=0.30; обзор Educational Psychology Review 2023). Closed recall до reveal — retrieval practice/testing effect (Roediger & Karpicke 2006). Changed-context cold repeat — «varying conditions of practice» из desirable difficulties Бьорк. План интуитивно воспроизвёл три самых надёжных эффекта literature.

P4 · Риск «зелёных тестов без Go» реален, и план его ловит ✅

Подтверждено: Makefile:33 Brain действительно делает exit 0 при отсутствии Go с сообщением «Docker CI will run go test» — то есть make check зелёный без единого выполненного Go-теста. Требование M1 про fail-closed container target — обосновано, не паранойя.

P5 · Silent locale fallback уже архитектурно исключён ✅

Живой Brain: точный join по локали, отсутствие строки → 404/исключение из выдачи, RU/EN полны 1591/1591, есть детектор «prompt==answer». Требование плана уже соблюдено — останется только не регрессировать.

P6 · Поглощение исторических планов почти полное ✅

CONTENT-EXPANSION, QUESTION-CAPABILITY-TASK, PRODUCT-INTEGRITY-UX, FULL-PRODUCT-REMEDIATION — требования корректно разложены по M0–M13 без потери существа (кроме ASPIRE-операционки, F4, и Review Workbench, F8). MASTER-PLAN Lab помечен RELEASED и легитимно объявлен superseded.

Происхождение «Plan 2026» и эволюция цикла

Исходный Plan 2026 лежит вне git — в Obsidian vault (iCloud~md~obsidian/Documents/Education/Plan 2026; путь зафиксирован в PRODUCT.md:90–91). In-repo производные: docs/reference/plan-2026-exercise-inventory.md, TIER1-CURRICULUM-SCOPE.md, vision.md. Ключевые пункты исходника, которые новый план сохранил:

  • Девятичастный эталонный lab: граф станций, версионный starter-workspace, deterministic checks, hint ladder, solution gate, trace view, explanation rubric, cold variant;
  • Prediction до первого запуска; AI никогда не открывает gate;
  • Cold repeat 2–3 / 7–10 / 21+ дней с привязкой к исходной попытке;
  • Timebox как часть упражнения; локальный AI; два тира (Tier 1 платформа → Tier 2 Project Books).

Одно тихое расхождение: канонический цикл в vision.md:56 и MASTER-PLAN.md:23 заканчивается на Repeat; новый план расширяет его до … Evidence → Journal → Cold repeat → Mastery. Расширение оправдано (Journal/Mastery — самые слабые звенья текущего продукта: 0 explanations, 0 mastered), но M0-глоссарий должен явно зафиксировать эту эволюцию терминов, чтобы две формулы цикла не жили параллельно.

12 рекомендаций «как сделать ещё лучше»

R1 · Исправить baseline до старта M0

В разделе 2 и M0-шагах: «Brain capabilities: 19» → «16 active canonical capabilities (+11 deprecated); 19 = capability bindings карточек». Одна строчка, но глоссарий начинается с неё.

R2 · Разрешить конфликт 15/20/19 ↔ G12 14/24 в M0 явно

M0 должен не просто «записать новые значения», а назвать, какой источник канонический (manifest Runtime vs матрица Lab), и пометить второй устаревшим. Иначе M1 получит два «правдивых» счётчика задач.

R3 · CoverageManifest обязан содержать mapping таксономий

Добавить в M8 обязательное поле: соответствие «12 областей плана ↔ 24 модуля TIER1-CURRICULUM-SCOPE ↔ 15 доменов проекции». Три параллельных списка областей — это следующая проблема «15/81 vs 12», которую план сам же закапывает.

R4 · Судьба ASPIRE-Jaeger — явное решение в M10

Либо включить AppHost/OTel Collector/Tempo decommission/SPM/storage-retention в M10 (расширив гейт), либо создать запись rejected-with-cause: "операционная консолидация отложена за пределы closure". Текущее молчание — скрытый scope hole.

R5 · Ready-to-learn: сразу server-owned формула

Вместо «определение требует уточнения» зафиксировать в M4 readiness compiler: ready := primary card structurally complete ∧ binding role assigned ∧ required locales complete. Метрика 989 всё равно никем не считается — замените её компилируемой, чтобы counters имели формулу и drill-down, как требует сам план.

R6 · Digest-pinning + threat model в M7

Критерий «pinned OCI image» уточнить до name:tag@sha256:… (тег мутабелен; известны container escape CVE вроде CVE-2024-21626). Добавить автоматический bump-path (Renovate/Dependabot digest PR), иначе пины протухнут. Отдельно задокументировать threat model текущего boundary («Docker socket, local-dev»). gVisor/runsc оставить отдельным Linux production upgrade path: официальный runtime требует Linux, поэтому на MacBook/Docker Desktop это не должен быть обязательный checkbox.

R7 · M0 дополнить operational hygiene

Три конкретных шага: (1) rebuild/recreate runtime-образа перед crawl (контейнер старее main — F5); (2) удалить зависшие smoke-контейнеры с фиксацией в baseline.json; (3) заменить misleading task-runtime.ui на shared observability.traceExplorerUrl без второго Jaeger-порта.

R8 · Вернуть Review Workbench как инструмент M6

Классификация 1 591 карточки с человеческим принятием решений требует batch-review поверхности: embeddings-assisted предложения группами, bulk accept/reject, очередь по disposition. Без него M6 растянется на недели ручной работы и будет искушать нарушить собственное правило «не auto-bind».

R9 · Порядок M8 — по данным, а не по интуиции

Coverage-score из artifact.json: Concurrency 3, PostgreSQL 3, Brokers/Cache/Auth/System Design 2, Docker/K8s/Networks/Observability/Algorithms/Angular 1. План ставит Docker (score 1) вторым, а PostgreSQL (score 3) — восьмым. Если нет педагогического основания — переупорядочить: Concurrency → PostgreSQL → Brokers → … Либо записать, почему данные проигнорированы.

R10 · Адаптивное планирование повторений — заложить фундамент сейчас

Фиксированный gate 48–72ч — правильный deterministic минимум. Но ступени 7–10/21+ день можно персонализировать моделью DSR (Difficulty/Stability/Retrievability) — алгоритм FSRS даёт те же ~20–30% меньше повторений при той же retention и встроен в Anki с 23.10; есть готовый ts-fsrs. Рекомендация: не менять план, но уже в M2 писать в evidence поля, нужные будущему планировщику (latency, self-grade, repeat outcome), чтобы миграция на FSRS была data-ready.

R11 · Interleaving — недостающий четвёртый desirable difficulty

Spacing ✓, varying context ✓, testing-as-event ✓ — но блокированная практика (все повторы одной области подряд) остаётся дефолтом. Добавить в M8 repeat variant policy опцию interleaved sessions (смешанные repeats разных capabilities) — это дешёвое усиление retention по Бьорк.

R12 · Портируемость доказательств: семантическое выравнивание, не имплементация

Спроектировать поля MasteryClaim/EvidenceBundle совместимыми по смыслу с Open Badges 3.0 AchievementCredential (Verifiable Credentials v2.0) и statement-моделью xAPI 2.0 (IEEE): subject, achievement, criteria, evidence[], issuer, provenance. Ноль нового кода сейчас — просто не выбирать имена/структуры, которые сделают будущий экспорт невозможным. Для CV/interview calibration из M13 это прямой мост.
